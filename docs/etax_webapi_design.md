# e-Tax（国税）納付情報登録依頼 API連携 設計メモ

ブラウザ自動操作（Playwright）は **e-Tax受付システムのブラウザ拡張機能必須の壁** により
不可能と判明したため、国税は **送受信モジュール相当のサーバー間HTTPS通信を純Python再実装**
する方式（A案）で実装する。地方税（eLTAX）は別途Playwright方式で実装済み。

## 実現可能性：確定（可能）

- 手続き送信（納付情報登録依頼）は、ブラウザ・拡張機能・電子証明書を使わず、
  **HTTPSのフォームPOST＋XML電文**で受付システムと直接やり取りする。
- ログインは **利用者識別番号＋暗証番号のみ**（拡張機能・証明書不要）。
- 納付情報登録依頼（様式 **TEZ500 Ver1.8**）は **電子署名不要**。
- 公式実装（CLCommunication.dll）は Windows専用C++のため使わず、プロトコルを再実装する。

## 接続先エンドポイント（CLCommunication.ini より）

```
ベースURL: https://uketsuke.e-tax.nta.go.jp
[Login]            /UF_APP/lnk/Menu
[DataSendRequest]  /UF_APP/lnk/datasend
[MessageBoxes]     /UF_APP/lnk/MsgboxItrnViewGmnPage
[ChangPassword]    /UF_APP/lnk/pwdchg
```
※ `login.e-tax.nta.go.jp`（ブラウザ用・拡張機能必須）とは別ホスト。

## プロトコル方式（受付if仕様書 より）

- 受付システムは画面ID単位のステートフルなHTML-form互換プロトコル。
- サーバはリクエストごとに **XMLレスポンス（画面）** を返す。各レスポンスの
  ヘッダー部に **引継ぎ情報（セッション）**、ボディー部に **リンク情報（次のPOST先URL）** を含む。
- クライアントは、直前レスポンスの引継ぎ情報とAction URLを使って次のPOSTを行う。
- サーバ証明書は SHA256 RSA / RSA2048。一定時間で自動ログアウト（タイムアウト）。

## 画面ID（状態遷移）

| 画面ID | 内容 |
|---|---|
| SU00S010 | 認証（利用者識別番号＋暗証番号でログイン） |
| SU00S020 | メインメニュー |
| SU00S070 | 申告等データ送信（← 納付情報登録依頼 TEZ500 を送信） |
| SU00S080 | 即時通知（受付番号・手続ID を取得） |
| SU00S090 | メッセージボックス一覧 |
| SU00S110 | メール詳細（納付区分番号通知）← 収納機関番号・納付番号・確認番号 |

## 送信フロー

```
1. POST /UF_APP/lnk/Menu   （利用者識別番号 + 暗証番号）
      → SU00S020 メインメニュー XML（引継ぎ情報・各リンクURL）
2. POST /UF_APP/lnk/datasend （TEZ500 納付情報登録依頼データ + 引継ぎ情報）
      → SU00S080 即時通知 XML（ステータス000=正常, 受付番号 XHC160, 手続ID XHC170）
3. POST /UF_APP/lnk/MsgboxItrnViewGmnPage → メッセージボックス
      → SU00S110 メール詳細（納付区分番号通知）
         収納機関番号・納付番号・確認番号（＝納付区分番号）を取得
```

## 納付情報登録依頼（TEZ500 Ver1.8）データ項目

| タグ | 内容 | 値の例 |
|---|---|---|
| DAB00010 | 税目 | 030=法人税, 040=地方法人税, 032=法人税(通算), 042=地方法人税(通算), 300=消費税及地方消費税 |
| DAB00015 | 税目区分 | （法人税通算時 "1"） |
| DAB00040 | 申告の種類 | 03=中間申告 等 |
| DAB00043 | 中間区分 | 1/2/3（申告のお知らせ PJB01100 から変換） |
| KAZEI_KIKAN_FROM/TO | 課税期間（自/至） | IT部要素（データ形式仕様 資料1参照） |
| DAB00050 | 本税額 | 金額 |

※ 申告のお知らせ（HOP080/HOP100/HOP130）を参照して自動作成する対応表が
   「XML構造設計書（受付発行_納付情報登録依頼のお知らせ参照作成について）」にある。

## 実装計画（フェーズ）

1. **設計（本書）** … エンドポイント・フロー・データ構造の確定 ← 済
2. **認証PoC** … `/UF_APP/lnk/Menu` に利用者識別番号＋暗証番号でPOSTし、
   拡張機能なしでメインメニューXML（引継ぎ情報）が返ることを実証。
   ここが通ればA案の成立が確定。
3. **本実装** … TEZ500電文生成 → `/UF_APP/lnk/datasend` 送信 → 即時通知の受付番号取得
   → メッセージボックスで納付区分番号取得 → 既存の e-Tax 送信履歴UIへ接続。
4. **送信試験環境**での検証（本番前）。

## 未確定・要確認（PoC/本実装で詰める）

- 認証リクエストの正確なパラメータ名（利用者識別番号・暗証番号のフォーム項目名）と
  文字コード・エンコード（form-urlencoded か multipart か、XMLラップの要否）。
  → 資料3 XSL構造設計書・資料_送受信モジュールで使用するパラメータ、実通信で確定。
- 送信データの圧縮（gzip）・Base64・電文包装（即時通知XMLへの内包形式）の要否。
- 送信試験（テスト送信）環境の利用申請と、テスト用利用者識別番号の要否。
- 受付システムWeb-API利用にあたっての届出の要否（開発者登録）。
